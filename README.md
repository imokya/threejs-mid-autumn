# 水调歌头 · 月白版

Three.js（WebGPU / TSL）交互场景，已整理为 Vite 项目。

## 快速开始

```bash
npm install     # 已执行过可跳过
npm run dev     # 开发服务器 → http://localhost:5173/
npm run build   # 产出 dist/
npm run preview # 预览 dist/
```

默认使用 **WebGL2** 以兼容内嵌浏览器；支持 WebGPU 的浏览器访问 `http://localhost:5173/?webgpu` 可切到 WebGPU 后端。右上角会显示当前后端。

## 相比原单文件版的改动

1. 内联 `<style>` → `src/style.css`，用 `<link rel="stylesheet" href="/src/style.css">` 引入。
2. 内联 `<script type="module">` → `src/main.js`，用 `<script type="module" src="/src/main.js">` 引入。
3. **删除 importmap**，改由 npm 依赖 `three@0.180.0` 解析。原 importmap 里 `three` 指向 `three.webgpu.js`，这一行为在 `vite.config.js` 中用 alias 还原，保证 `three` / `three/webgpu` / `three/addons/*` 共用同一份实例。
4. 月面贴图由运行时相对路径 `./assets/moon-lroc-2k.jpg` 改为 Vite 静态导入 `import moonMapUrl from '../assets/moon-lroc-2k.jpg'`，构建时自动带哈希。
5. 页面头部的运行时错误提示脚本保持内联不变。
6. 旧的 `index.original.html` 与 `vendor/` 移入 `legacy/`（该目录内相对路径未改，单独在 `legacy/` 下用 `python3 -m http.server` 起服务仍可运行）。

## 性能

### 加载

- 程序月面纹理（2048×1024 逐像素噪声 + 1800 个陨坑 + 局部模糊）原本每次启动都要算，算完立刻被 NASA 影像替换——现在只作兜底：影像加载失败时才真正生成。这一项约占纹理阶段六成以上耗时。
- 兜底生成会临时记录随机流位置并在生成后拨回，因此场景里林、石、灯的随机细节不受影响。
- 纹理生成改成 `async`，分批 `await nextFrame()` 让出主线程，片头不再整段卡死。
- 控制台会打印各阶段耗时表（`阶段 / 耗时毫秒 / 累计毫秒`），可直接看出瓶颈在哪一段。

### 帧率

| 项目 | 高档 | 低档 | 最初 |
| --- | --- | --- | --- |
| 像素比上限 | 1.75 | 1.0 | 2.0 |
| 像素比下限（自适应） | 1.0 | 0.85 | 1.0 |
| 多重采样 | 2x | 关 | 4x |
| 阴影贴图 | 1280 | 896 | 2048 |
| 阴影刷新 | 每 3 帧 | 每 4 帧 | 每帧 |
| 水面反射分辨率 | 0.32 | 0.24 | 0.5 |
| 水面反射刷新 | 每 2 帧 | 每 3 帧 | 每帧 |
| 雾片数量 | 34 | 20 | 34 |
| 远景云数量 | 9 | 6 | 9 |

**1. 水面反射隔帧复用**

反射本质是「把整个场景换个机位再画一遍」，是全场最贵的一笔。水面已经被三层噪声扭曲、外面还套了菲涅尔混色，反射贴图晚一帧几乎不可能看出来，于是隔帧重算，中间帧直接沿用上一张。

实现上挂在 `reflection.reflector.updateBefore` 上，节拍由主循环的 `frameNo` 驱动（每动画帧 +1），而不是数 `updateBefore` 被调用的次数——后者一帧内可能被多个绘制对象触发，次数不稳定。另外跳过时必须返回 `undefined` 而不是 `false`：three 的 `updateBeforeNode` 看到 `false` 会认为「本帧没执行」，下一个绘制对象还会再调一次，等于白省。

**2. 程序噪声降阶**

场里有大量「大屏占比 × 多阶 3D 噪声」的着色器：9 片远景云、34 片雾、贴水薄雾平面、云海、远山材质，全是 4~5 阶的 `mx_fractal_noise_float`，且都是重叠加色的透明面片。

fbm 每一阶振幅是上一阶的一半，累加后方差按平方和增长：振幅序列 1, 0.5, 0.25, 0.125, 0.0625 对应的标准差是 1.154 / 1.152 / 1.146 / 1.118。也就是说

- 5 阶 → 3 阶：噪声标准差只变化 **0.7%**（云）
- 4 阶 → 3 阶：只变化 **0.15%**（雾、贴水薄雾、远山）
- 5 阶 → 3 阶（云海）

最高那两阶只是给噪声叠一层高频细纹，落在 `smoothstep` 的过渡带里几乎不产生位移，却占掉这些着色器四成以上的运算量。唯一保留 5 阶的是「过月之云」——它是单一主角，不吃数量优势。

**3. 减少透明面片的叠加层数（仅低档）**

雾片 34→20、远景云 9→6。这两处改动会**改变画面构成**，所以只放在低档。实现上把「抽随机数」和「造面片」拆开了：低档少造面片，但随机数照常按原顺序抽完，因此下游场景（林木、山石、塔桥、舟人）的随机细节一个都没变。

**4. 其他**

- 画布自带的 MSAA 已关闭：抗锯齿由后期通道负责，最终画面只是一个全屏四边形，画布再留一份多重采样缓冲纯属浪费。
- 像素比运行时自适应，取样窗口从 1 秒缩到 0.7 秒（一两拍卡顿就能触发降档，而不是等满一秒），升档要求连续 6 个窗口的稳定期，避免在阈值上反复抖。高档下限 1.0，低档 0.85。
- 阴影按帧隔刷新。注意 three r180 的阴影走 `ShadowNode`，闸门挂在 `moonLight.shadow` 上，`renderer.shadowMap.autoUpdate` 已不被读取。
- 去掉了一处每帧冗余的整树 `updateMatrixWorld`（`getWorldPosition` / `getWorldQuaternion` 内部已沿父链自更新）。

### 怎么看瓶颈

打开 `?stats`，左上角两行：

```
58 FPS · high · WEBGPU · 1.50x
CPU 3.7ms/帧 · 268 绘制 · 940k 三角
```

- **FPS 对应的帧时长 ≫ CPU 耗时** → 瓶颈在 GPU（填充率/着色器），优先动噪声阶数、像素比、反射。
- **CPU 耗时接近帧时长** → 瓶颈在 JS 侧，优先动粒子数量与逐帧矩阵写入。
- **绘制次数偏高**（>300）→ 瓶颈可能在提交侧，考虑把船体静态部件按材质合并。

`CPU` 量的是「CPU 把一帧交出去」的耗时（场景更新 + 提交绘制命令），不含 GPU 真正画完的时间。

### 下一根杠杆（尚未动手）

1. **点光源 19 盏**。每盏都会进入所有标准材质的逐像素光照循环，代价按盏数线性叠加。`?lights=lean` 可以跳过两岸民居那 6 盏（19→13）实测这一项的开销——注意它会压暗两岸屋檐下的暖光，是个 A/B 工具而非默认档。
2. **花瓣/河灯/孔明灯的逐帧矩阵**目前在 CPU 上算完再整包上传（800+52×2+150 个矩阵）。搬到顶点着色器里计算可以省掉这部分 CPU 与上传带宽，但落水判定用到 `shoreX/rightX`，需要一并改写。
3. **船体静态部件按材质合并**，减少绘制次数。

| URL / 位置 | 作用 |
| --- | --- |
| `?stats` | 左上角显示 FPS、档位、后端、像素比、CPU 耗时、绘制次数、三角数、东坡取景守卫读数 |
| `?quality=low` | 强制低档 |
| `?quality=high` | 强制高档（移动端/低核数设备默认低档） |
| `?webgpu` | 切换到 WebGPU 后端 |
| `?lights=lean` | 跳过 6 盏岸边点光源，用于实测光照循环开销（会压暗两岸暖光） |
| `TUNE`（src/main.js 顶部） | 上表所有数值 |

一次性对照：`?stats&quality=low` 与 `?stats&quality=high` 各看十几秒，就知道这台机器上段位差多少。

`?stats` 第三行是**取景守卫**的实时读数：东坡是否在画面内、机位偏离他正后方的角度。正常应为「背面 -0.7~-0.95」；一旦出现「正面半球」并伴随控制台告警，说明有镜头摆到了他脸前。

## 画面调整（第三轮）

### 1. 建筑提亮 —— 改 `ARCH` 表

夜景里建筑偏暗、看不准材质，于是给建筑类材质统一加了一层**基色增益 `gain`**（`color.multiplyScalar`）与**自发光底 `glow`**（`emissiveNode`）。后者取材质自身反照率当底光，不吃灯光、不产生额外的光照计算开销，效果是暗部被托起来而不是被"打亮"。

| 材质 | gain | glow | 说明 |
| --- | --- | --- | --- |
| `bracket` 斗拱 | 1.70 | 0.075 | 提得最多，木构细节最密 |
| `tile` 筒瓦 / `ridge` 正脊 | 1.62 / 1.60 | 0.090 / 0.075 | 屋面是主视觉面 |
| `copper` / `under` / `lacquer` | 1.55 / 1.55 / 1.26 | 0.085 / 0.080 / 0.105 | 铜脊、檐下、朱漆 |
| `lattice` / `redCap` / `pagodaWall` | 1.40 / 1.40 / 1.35 | 0.080 / 0.055 / 0.100 | 门窗棂、灯罩、塔身 |
| `wood` / `plank` / `canopy` | 1.30 / 1.32 / 1.32 | 0.080 / 0.080 / 0.065 | 梁枋、板壁、席帘 |
| `stone` / `stoneStep` / `wall` | 1.30 / 1.20 / 1.22 | 0.050 / 0.055 / 0.105 | 铺地台基、踏步、白墙 |
| `bridge` / `gold` | 1.18 / 1.18 | 0.048 / 0.055 | 石桥、金饰（金饰另给暖色底） |

**山水、草木、水面、天空、乌篷船一律没动**，夜色基调不变。想更亮或更暗，只改这张表里的数字：`gain = 1` 且 `glow = 0` 就是完全关掉。

### 2. 镜头不再给到东坡正面

东坡始终朝着月亮（`PF` 就是脸的方向）。用 `face = 机位方向 · PF` 量化：`-1` 正后方、`0` 正侧面、`+1` 正前方。逐帧复算 168 秒时间线后发现，全片只有「起舞弄清影」这一镜在切镜瞬间越到了侧面（`face ≈ -0.09`），因为上一镜在雷峰塔——正好是他正面那一侧。

改法是把该镜的机位从侧面 `atan2` 取景换成 `behind(d, side, up)` 背面取景，起幅放在他身后 20 米，整段飞行都在背后完成，再缓缓推近、沿后肩横移半程：

```js
// 改后：face 约 -0.76（背面）
cam: (u) => ({ p: behind(lerp(20, 4.4, u), lerp(-7, -3.4, u), lerp(5.5, 1.7, u)), t: ahead(1.2, 0.55), fov: lerp(34, 42, u) })
```

另外加了 `guardRear()` 守卫：每帧把东坡投影到 NDC，只要他在画面内且机位进了正面半球，控制台直接点名「第 N 镜偏离正后方多少度」。将来再改镜头，摆错位置会立刻暴露，不用靠眼睛盯。`dir.free`（自由相机）状态下不计。

### 3. 飞鸟

三群共 9 只（4 + 3 + 2），各自沿椭圆巡飞，高度、周期、体型、环绕方向都不同，会缓慢错开。第一群的椭圆**正好穿过月面视线**，所以每圈都会有一次横越月亮。

- **扇翅**：身体 + 左右翼三组 `InstancedMesh`，CPU 每帧写 27 个矩阵，翼绕肩旋转 `f = sin(t·flap + fp) × 0.52`，起落之间略微收拢。之所以不走顶点着色器，是因为实例网格里 `positionNode` 拿到的是**已乘过实例矩阵**的坐标，再 assign 会把鸟整个撕开（详见 `src/main.js` 里那段注释）。
- 材质是 `MeshBasicNodeMaterial` + 深色（`0x0a0f1c`）、`fog: false`：纯逆光剪影，过月时是干净的黑色，也零光照开销。

要加鸟只改 `FLOCKS` 表：`[只数, 圈心 x/z, 半径 rx/rz, 高度, 周期秒, 起始相位, 体型, 环绕方向]`。

### 4. 远处不可见处减模

原则：**随机数的抽取顺序与次数完全不变**，只是条件性地少造面片，所以近景细节一像素都不动。

| 部位 | 改动 | 依据 |
| --- | --- | --- |
| 近山 | 340×140 → **280×112** | 山体本身是低频大曲面 |
| 中景山 | 240×64 保持 | 会在画面中占比可观 |
| 远景山 | 260×60 → **130×32** | 最近也在 300 米外 |
| 夕照山 + 雷峰塔基座 | 200×200 → **160×160** | 镜位最近 46 米且多为俯视 |
| 远景林木 | 两级 LOD：圈内 80 面 / 圈外 **20 面** | 半径 210 米外只留轮廓 |

远景林的做法是按到舟行中心的距离分流到两个实例网格：`farAway(x,z)` 判定，圈外走 `FOLIAGE_LO`（`IcosahedronGeometry(1, 0)`，20 面）与无 `flatShading` 的 `M.foliageFar`。实测圈外占比：近山林木 45.3%、岸上林木 2.4%。

## 画面调整（第四轮）

- **东坡换为外部模型** `assets/sushi.glb`（单网格静模、立姿举杯，面朝 +Z），缩放到约 1.76m，立于船头甲板；衣摆用 `positionNode` 随风轻摆，整体有呼吸般的微晃。方灯、绳盘挪离船头给他让出站位。放孔明灯一镜里，灯从他举杯的手上方升起。
- **建筑再提亮**：`ARCH_BOOST`（基色 ×1.15、底光 ×1.4），只作用于 `ARCH` 表里的建筑材质。
- **云**：天空着色器里新增「天穹云层」——视线投到高空平面取噪声（域扭曲 fbm + 反 Worley），朝月方向偏移再采样一次得出迎月面，云边发亮、云腹偏暗。云量刻意偏少；月亮周围约 10°~20° 强制留出晴空，远景云片也避开这一圈，「过月之云」改为从月下掠过，**云不遮月**。
- **雾**：后期加了一层基于深度的高度雾（解析积分，一次全屏计算），浓度调得很淡，只让山脚和水面有一点薄霭；原雾片透明度降到 0.35 倍。`?fog=off` 可关闭做对照——实测开关前后帧率无差别。
- **署名**：右下角「CREATED BY XINGOR 行歌」，链接 https://www.xingor.dev（新标签页打开），样式在 `src/style.css` 末尾 `#credit`。
- **月边更清**：天空月晕、高度雾前向散射、云的月光银边都收窄减弱，月面亮度略压以少吃辉光。
- **修正画面拉伸**：画布尺寸有多条变更路径（resize 事件、像素比自适应、内嵌浏览器改视口时可能不发 resize），之前相机宽高比可能停在旧值，整幅画面被横向拉伸、月亮成椭圆。现在 `syncAspect()` 逐帧比对并同步。
